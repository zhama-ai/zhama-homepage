# 发布官网联系页面与线索通知

联系表单分为“咨询内容”和“联系方式”。咨询主题、咨询内容和联系方式必填。联系方式合并为一个普通文本框，填写邮箱或手机号，不校验邮箱、号码格式，仅保留非空、长度与单行文本的安全限制；不自动添加联系方式类别或备注。右侧顺序为联系方式、期望回复时间、昵称，昵称选填且位于最后。期望回复时间默认显示“越快越好”，点击字段打开统一日历弹层，在同一弹层内选择日期和“上午 / 下午”，不在页面单独显示时段选项，也不提供具体时分。选择日期后默认上午，可切换下午，点“完成”或弹层外部收起，字段显示日期与时段。邮件和飞书使用“YYYY-MM-DD 上午”或“YYYY-MM-DD 下午”。可通过清除按钮恢复默认；不选日期时按“越快越好”提交。必填错误在字段下方显示，不使用浏览器默认校验气泡。

新线索分别通知 `contact@zhama.com`、`xuguoyong@zhama.com`，并通过飞书应用机器人向“市场线索”群发送原生卡片。卡片采用飞书 JSON 2.0，宽度模式为 default（桌面宽度上限 600px，原为 compact 400px）；顶部标题保留一个线性图标；字段与标题文字左对齐，取消分类标题与灰色背景。线索来源和期望回复时间并排两列；联系方式展示填写原文，旧记录中的邮箱与电话兼容合并展示；线索主题与正文各占整行。昵称填写后保存在记录与邮件中，留空时不显示“未留昵称”；群卡片不展示昵称。历史“即时”请求继续显示橙色回复时间和“即时联系”标签，当前表单不再提供该独立选项。邮件正文使用与卡片相同的回复时间。卡片内容需要飞书 7.20 或更新客户端。空回复时间显示“越快越好”，既有记录不改写。

## 联系入口和来源路径

顶部“关于我们”展开为“关于我们”和“联系我们”两个入口，同时保留独立的“联系我们”按钮。手机端保留顶部“联系我们”，登录入口位于展开导航内；页脚新增联系表单链接。首页、产品、方案、报价及资源页的既有咨询入口继续指向对应语言的联系页。

网站在当前标签页记录实际访问的站内页面，以及进入页面时所用的导航分组。例：首页 → 解决方案 → 银行解决方案。未经过首页时不补加首页；直接打开联系页时记录“直接进入联系页”。连续刷新不重复记录，实际返回先前页面则保留这次访问。最近30分钟的会话最多保留20个路径节点，不记录查询参数、片段、表单内容或站外浏览历史。提交时才将来源信息随线索发送到服务器。

每条线索的 sourceTrail 保存页面名称、站内路径及节点类型；referrer 保存进入联系页前的站内页面地址。邮件只展示“来源路径”；飞书卡片第一行两列为“线索来源 / 期望回复时间”，第二行两列为“联系方式 / 来源路径”，不展示来源网址或联系入口。主题与咨询正文保持整行。既有未记录来源的线索不补造访问历史。

浏览器限制会话存储时，使用可取得的当前来源页；跨标签页仅能依据该标签页能取得的来源信息。此记录是访客提交时携带的来源线索，不是独立核验的访问审计。

## 提交成功弹窗

接口确认线索已保存后，联系页原位打开居中确认弹窗，背景添加半透明蒙层，保留表单作为上下文，不跳转全屏状态页。弹窗显示“信息已提交”“我们会尽快与您联系。”和唯一的“确定”按钮。失败时保留表单内容并显示错误，不打开成功弹窗。

正常站内进入时，“确定”通过浏览器历史返回实际来源页。来源为站外页面时也只通过历史返回，不将站外地址作为脚本跳转目标。直接打开联系页且没有来源时返回对应语言首页。联系页切换语言后返回先前记录的站内来源地址，避免回到联系表单。

弹窗使用原生 dialog 和 showModal，打开时焦点进入确定按钮，背景不接收操作；Escape 关闭弹窗并将焦点还给提交按钮。返回信息保存在当前标签页会话与联系页历史状态中，不含联系方式及咨询正文；刷新后不会自动重现成功弹窗。旧的 /<语言>/contact/submitted/ 地址重定向到联系页，并继续排除站点地图。

## 本机验证

在项目根目录执行：

```sh
npm ci
npm run contact:verify
npm run build
npm run preview
```

打开 `http://127.0.0.1:4350/zh/contact/`。`npm run preview` 同时提供构建后的静态页面和 `/api/contact` 接口。开发时使用 `npm run dev`，同一端口也接入消息接口。表单统一提交到 `/api/contact/`，满足 Astro 开发服务器的尾斜杠规则；生产消息服务同时接受带或不带尾斜杠的地址。

英文和繁体页面分别为 `/en/contact/`、`/zh-Hant/contact/`。价格页的 `?plan=community`、`?plan=subscription`、`?plan=enterprise` 会带入标题，`#enquiry-form` 定位表单。

提交前的必填检查不发送消息。有效提交会真实发送两封邮件及一条群通知；验证内容应明确标注联调目的，避免被当作客户商机。

## 保存消息配置

当前本地配置保存在项目根目录 `.env.contact.local`，权限为 `600`，已加入 Git 和 Docker 构建上下文的忽略规则。部署时通过受控通道将该文件放到目标项目根目录，不放入 `dist/`。

| 配置项 | 当前用途或取值 |
| --- | --- |
| `SMTP_HOST` | `smtp.exmail.qq.com` |
| `SMTP_PORT` | `465` |
| `SMTP_SECURE` | `true`，使用 TLS |
| `SMTP_USER`、`SMTP_FROM` | `xuguoyong@zhama.com` |
| `SMTP_PASS` | 企业邮箱客户端授权码，保存在受控配置中 |
| `CONTACT_EMAIL` | `contact@zhama.com` |
| `CONTACT_EXTRA_EMAIL` | `xuguoyong@zhama.com` |
| `FEISHU_APP_ID`、`FEISHU_APP_SECRET` | 当前飞书自建应用凭据，保存在受控配置中 |
| `FEISHU_CHAT_ID` | 当前“市场线索”群的 ID，已保存到本地配置 |
| `RATE_LIMIT_MAX`、`RATE_LIMIT_WINDOW` | 默认每个来源 IP 每 60000 毫秒允许 5 次请求 |
| `CONTACT_DATA_DIR` | 默认 `.contact-data/`，保存线索及各通道投递状态 |

飞书应用需要启用机器人、加入通知群，并发布包含 `im:chat:readonly` 和 `im:message:send_as_bot` 权限的版本。修改配置后重启消息服务。

## 发布静态页面和消息服务

需要 Node.js 22.23.4 或更高版本；容器采用 Node.js 24。目标服务器需要 Docker Compose，现有网站由宿主机 Nginx 提供 HTTPS 服务。

1. 执行 `npm run build`，将完整 `dist/` 发布到网站静态目录。
2. 保留项目的 `server/contact/`、`shared/`、`deploy/contact/`、`package.json` 和 `package-lock.json`，将本地消息配置安全放入目标项目根目录。
3. 在目标项目根目录启动消息服务：

   ```sh
   docker compose -f deploy/contact/compose.yml up -d --build
   docker compose -f deploy/contact/compose.yml ps
   curl --fail http://127.0.0.1:4351/health
   ```

4. 将 `deploy/contact/nginx.conf` 的两个 `location` 块加入 `www.zhama.com` 现有 HTTPS `server` 块，再执行 `nginx -t` 和 `nginx -s reload`。网站根目录继续指向 `dist/`；只将 `/api/contact`、`/api/contact/` 转发到消息服务。
5. 打开正式联系页面，提交一条注明发布核对用途的记录，核对邮件和群通知中的线索编号。

容器端口只绑定宿主机 `127.0.0.1:4351`。Compose 使用命名卷 `contact-leads` 保存线索；更换容器不删除该卷。Nginx 覆盖转发 IP 头后，容器中的 `CONTACT_TRUST_PROXY=true` 才能按访客 IP 限流。

不使用 Docker 时，可在受进程管理器托管的项目根目录执行 `npm run contact:serve`。接口默认绑定 `127.0.0.1:4351`，仍需配置上述 Nginx 转发，并将 `.contact-data/` 保存在持久磁盘。

一个数据目录只运行一个消息服务实例。开发、预览和独立接口服务不要同时使用同一个数据目录；多副本部署需改用共享事务存储和队列。

## 核对接收与投递状态

接口仅在有效内容成功写入持久存储后返回 `success: true` 和 `leadId`。这表示线索已收到；邮件和群通知随后独立发送。缺少邮件配置或保存失败会返回错误，表单保留输入内容。

每条记录在 `.contact-data/<leadId>.json` 中保存两个邮箱及飞书的状态、通道消息 ID 和最后错误码。`delivered` 表示对应服务已确认接收，不等同于收件人已阅读。该目录包含联系方式和需求正文，不作为静态资源发布。

失败通道从 15 秒开始指数退避，最大间隔 1 小时；服务重启后继续检查未完成通道。已确认通道不参与正常重试。浏览器对同一内容的重试沿用提交 ID，飞书通知也带相同 UUID。

如果远端已接收但本地尚未保存回执时进程中断，邮件重试仍可能重复；保留相同 `Message-ID` 和线索编号便于核对。不要把该机制视为跨系统的严格一次投递保证。

运行 `docker compose -f deploy/contact/compose.yml logs --tail=100 contact` 查看线索编号和通道状态。日志不输出客户正文、邮箱授权码或飞书凭据。`/health` 仅检查必要配置是否齐全；`npm run contact:verify` 进一步检查 SMTP 认证和飞书机器人群访问。
